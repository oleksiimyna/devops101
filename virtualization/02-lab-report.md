## Завдання 2. Зламати й відновити DNS — виконано

Перед експериментом створив snapshot `clean` з описом «Робоча Ubuntu Server після зміни hostname».

### Навмисна поломка

Видалив конфігураційний файл DNS:

```bash
sudo rm /etc/resolv.conf
```

Перевірив розв'язання доменного імені:

```bash

```

Отриманий результат:

```text

```

Скріншот: `screenshots/02-broken.png`.

### Відновлення

Вимкнув VM, відновив snapshot `clean`, знову запустив Ubuntu та повторив перевірку:

```bash
ping -c 2 ubuntu.com
```

Результат після відновлення:

```text
2 packets transmitted, 2 received, 0% packet loss
```

Скріншот: `screenshots/02-restored.png`.

**Висновок:** після видалення `/etc/resolv.conf` DNS-розв'язання не працювало. Після відновлення snapshot `clean` домен `ubuntu.com` знову успішно розв'язувався.

## Завдання 3. Перевірка мережевих режимів — виконано

### NAT

Адреса Ubuntu:

```text
enp0s3  UP  10.0.2.15/24
```

Перевірки:

```bash
ping -c 2 1.1.1.1
ping -c 2 ubuntu.com
ip route
ping -c 2 10.0.2.2
ping -c 2 192.168.0.171
```

- Доступ до `1.1.1.1`: успішно, 2/2, 0% втрат.
- DNS та ping `ubuntu.com`: успішно, 2/2, 0% втрат.
- Default gateway: `10.0.2.2`; ping до шлюзу успішний.
- Ubuntu → Windows-хост `192.168.0.171`: успішно, 2/2, 0% втрат.
- Windows-хост → NAT-адреса VM `10.0.2.15`: тайм-аут, 100% втрат.

### Bridged

Ubuntu отримала адресу `192.168.0.137/24`, gateway `192.168.0.1`.

- VM → інтернет (`ping 1.1.1.1`): успішно, 2/2, 0% втрат.
- Windows → VM: `Destination host unreachable`.
- VM → Windows `192.168.0.171`: 0/2, 100% втрат.

Отже, під час цієї перевірки повний зв'язок між Windows і VM у режимі Bridged не підтверджено.

### Host-only

Ubuntu отримала адресу `192.168.56.101/24`. `ip route` показав лише маршрут локальної мережі `192.168.56.0/24`; default route відсутній.

- Інтернет через Host-only: відсутній.
- Windows-хост → VM `192.168.56.101`: успішно, 4/4, 0% втрат, менше 1 ms.
- VM → Windows Host-only адреса `192.168.56.1`: 0/2, 100% втрат.

Отже, ICMP-зв'язок Host-only підтверджено лише в напрямку Windows → Ubuntu; зворотний напрямок не підтверджено.

### Підсумкова матриця спостережень

| Режим | IP VM | Інтернет | Хост → VM | VM → хост |
|---|---|---|---|---|
| NAT | `10.0.2.15/24` | Так | Ні, тайм-аут | Так, до `192.168.0.171` |
| Bridged | `192.168.0.137/24` | Так | Ні, `Destination host unreachable` | Ні, 100% втрат |
| Host-only | `192.168.56.101/24` | Ні, немає default route | Так, 4/4 | Ні, 100% втрат |

**Висновок:** режими мережі дають різні сценарії доступу. У цій лабораторній роботі NAT забезпечив вихід VM в інтернет; Host-only забезпечив перевірений зв'язок від Windows до VM; у Bridged доступність VM з хоста не підтвердилася. Результати ping можуть залежати від конфігурації мережі й брандмауера.

## Завдання 4. Збільшення ресурсів і питання зменшення диска — виконано

```text
Swap:          2.6Gi          0B       2.6Gi
```

Скріншот: `screenshots/02-resources.png`.

**Висновок:** Ubuntu бачить 4 процесори та приблизно 5.3 GiB RAM. Це підтверджує, що гостьова ОС побачила нові ресурси VM.

### Перевірка диска та пояснення щодо зменшення

Команди:

```bash
lsblk
df -h
```

Основні результати:

- `sda` — 30 GB;
- `sda1` — 1 MB;
- `sda2` — 2 GB, змонтований як `/boot`;
- `sda3` — 28 GB;
- логічний том Ubuntu, змонтований як `/`: 14 GB;
- коренева файлова система `/`: 5.7 GB використано, 7.4 GB доступно, 44% використання.

У Virtual Media Manager:

- формат: VDI;
- тип: динамічно виділюваний;
- віртуальна місткість: 30 GB;
- фактичний розмір основного VDI-файлу на хості: приблизно 5.87 GB.

**Пояснення:** не можна безпечно просто зменшити віртуальну місткість диска з 30 GB до 10 GB, навіть якщо даних зайнято лише близько 5.7 GB. Дані можуть бути розташовані в різних ділянках диска, а всередині є розділи, LVM і файлова система. Якщо обрізати кінець диска, можна втратити дані, що лежать за новою межею. Це як бігова доріжка довжиною 30 км: якщо бігуни разом займають 5 км, це не означає, що всі вони знаходяться на перших 5 км. Спочатку потрібно перемістити або перебудувати дані так, щоб вони помістилися в межах меншого диска.

Якщо потрібно справді зменшити віртуальну місткість, можна створити новий менший віртуальний диск, перенести на нього систему та дані, перевірити успішний запуск і лише після цього від'єднати та видалити старий диск. Якщо ж потрібно лише звільнити місце на SSD Windows, можна позначити вільні блоки нулями та виконати Compact для динамічного VDI. Це може зменшити фактичний файл на хості, але не змінює віртуальну місткість 30 GB.

## Завдання 5. Експорт OVA та план міграції — виконано

Експортовано VM `devops-lab-manual` у файл `devops-lab-manual.ova`.

- Формат: Open Virtualization Format 1.0;
- розмір OVA у Windows Explorer: `3 078 213 KB` (приблизно `2.94 GiB`);
- віртуальна місткість диска: `30 GB`;
- фактичний розмір основного VDI у Virtual Media Manager: `5.87 GB`.

**Чому розміри різні:** 30 GB — це віртуальна місткість диска, а не фактичний розмір файлу. Під час експорту VirtualBox пакує опис VM та образ диска в OVA; образ диска в експорті зберігається у стисненому форматі. Тому OVA може бути меншим за VDI-файл на хості.

### Мій план перенесення VM на ноутбук колеги

Для початку я б експортував свою VM у форматі `.ova`. Потім переніс би цей файл на ПК колеги та імпортував його через VirtualBox. Оскільки це копія моєї VM, мережеві карти потенційно можуть мати однакові MAC-адреси, а це може спричинити конфлікт, якщо обидві VM працюватимуть в одній мережі. Під час імпорту потрібно перевірити, щоб копія отримала нові MAC-адреси. Також потрібно змінити мережевий режим з NAT на Bridged, щоб обидві VM підключилися до спільної фізичної мережі, а роутер міг видати кожній окрему IP-адресу. Бажано також змінити hostname у копії, щоб не плутати, де чия VM.

## Завдання 6. Прогноз кількості VM — перевірено частково

Початкові показники хоста до запуску тестових VM за Windows Task Manager:

- фізична RAM: 32 GB (31.9 GB у Windows);
- використано RAM: приблизно 11.8–11.9 GB;
- доступно RAM: приблизно 20.1 GB;
- CPU: AMD Ryzen 7 5700X3D, 8 фізичних ядер, 16 логічних процесорів;
- початкове завантаження CPU: приблизно 1%.

Було створено 6 Linked Clones від основної VM. Кожен клон мав 2 vCPU та 2 GB RAM; оригінальна VM залишалася вимкненою. Усі 6 тестових VM запущено одночасно.

Після запуску шести VM Windows Task Manager показував:

- використання RAM: приблизно 17.0 GB (53%);
- доступно RAM: приблизно 14.9 GB;
- CPU: близько 8–9% у момент скриншота.

Отже, приріст використання RAM становив приблизно 5.1–5.2 GB для шести VM, або орієнтовно 0.8–0.9 GB на VM за умов цього тесту. Це середня оцінка за одним спостереженням, а не фіксований обсяг для кожної VM.

**Мій прогноз:** при орієнтовному навантаженні на 0.8 GB RAM від однієї VM і невеликому навантаженні на CPU, за підрахунками, можливо запустити до 21 VM, коли вже почне проявлятися обмеження по RAM. Але для адекватної працездатності я б орієнтувався приблизно на 15 VM. Окрім споживання ресурсів самими VM, потрібно враховувати ресурси Windows, VirtualBox та сторонніх фонових процесів.

**Обмеження висновку:** одночасну роботу шести VM перевірено фактично. Кількість 15 або 21 VM не тестувалася, тому це прогноз, а не підтверджена межа комп'ютера. Початковий прогноз із попереднього завдання не був записаний, тому цей прогноз сформовано після проведеного експерименту.
